# 优选IP 详解

左侧导航第一项。给它一批候选地址，它还你一份按评分排序、可直接填进客户端的列表。

---

## 测什么，不测什么

| 测 | 不测 |
|---|---|
| 你的设备到 Cloudflare 边缘节点的延迟 | Cloudflare 到源站的延迟 |
| 该 IP 的下载吞吐 | 你实际访问网站的真实速度 |
| 丢包率 | 被运营商 QoS 后的表现 |

**测速结果反映的是「这一段链路」的质量**，不等于你使用时的完整体验。详见 [原理与限制](How-It-Works)。

---

## 四个阶段

点「开始测速」后，进度条依次经历：

```text
① 加载 IP 来源   抓取在线列表、展开网段、按 IP 去重
② 域名探测       （可选）只保留真正服务你域名的 IP
③ 延迟测速       TCPing 或 HTTPing，多次取平均
④ 下载测速       （可选）对延迟最低的 N 个实际下载
```

每一步都可以在进度条下方看到当前数字。任何一步结果为 0，结束时会弹诊断窗。

## 八种 IP 来源

在「IP 来源」区域勾选，可多选，**全部合并后按 IP 去重**。

| 来源 | 内容 | 典型数量 | 需要联网 |
|---|---|---|---|
| **内置 ip.txt**（必选） | 程序目录下的 CF 网段，每个 /24 随机取 1 个 | ~6000 | 否 |
| 内置 ipv6.txt | IPv6 网段 | 视文件而定 | 否 |
| **优选IP BestIP** | 抓取 bestcf.pages.dev 的「优选IP BestIP」区块，排除 GitHub 链接 | ~1200 | 是 |
| **Cloudflare 官方 IP 段** | `api.cloudflare.com/client/v4/ips` 实时网段 | 数百 | 是 |
| **cmliu CF-CIDR** | 社区维护的补充网段，覆盖面通常比官方更广 | 数百 | 是 |
| **CF 官方域名池** | BestCF 维护的真实 CF 域名清单，DoH 解析成 IP，只保留 CF 网段的 | ~870 | 是 |
| **自定义 IP 源** | 自己填任意列表 URL，每行一个 | 自定 | 是 |
| **手动指定 IP 段** | 直接输入 `IP`、`CIDR` 或 `IP:端口`，英文逗号分隔 | 自定 | 否 |

### CF 官方域名池是什么

来自 [cmliu/CF-Pages-BestCF](https://github.com/cmliu/CF-Pages-BestCF) 的 `cf_domains.txt`，是一份**真实托管在 Cloudflare 上的域名清单**（约 420 个）。

抓取时会按顺序尝试国内可用的镜像：

```text
jsDelivr → gh-proxy.com → ghfast.top → ghproxy.net → raw.githubusercontent.com
```

拿到域名后通过 DoH 解析成 IP。其中约 4% 的域名已经不在 Cloudflare 上（CNAME 到了 AWS / Akamai），解析结果会被**过滤掉**，不占用测速名额。

**定位**：数量大、可用率高（实测 426 个域名 → 873 个 IP），但**延迟一般**，适合当兜底，不适合追求极致延迟。

> 完整抓取约 40 秒，之后本次运行内复用缓存。

### 去重与端口优先级

同一 IP 出现多个端口时，保留顺序：

```text
443 → 8443 → 2053 → 2083 → 2087 → 2096
```

### 在线来源的缓存

在线来源在**每次打开程序后的第一次测速**时抓取，之后复用，不再重复请求。

修改来源配置或重开程序才会重新抓取。

### 自定义 IP 源支持什么

每行一个 URL，抓回来的内容支持：

```text
1.2.3.4                        纯 IP
1.2.3.4:8443                   带端口
1.2.3.4/24                     CIDR 网段
example.com:443                域名（会通过 DoH 自动解析成 IP）
```

域名解析走**阿里 DoH 优先，Cloudflare DoH 兜底**。

### 手动指定 IP 段

一个输入框，英文逗号分隔：

```text
104.16.0.1,104.17.0.0/24,1.2.3.4:8443,2606:4700::1
```

## 延迟测速

### 两种模式

| 模式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **TCPing**（默认） | 测 TCP 三次握手耗时 | 快、不消耗 CF 配额 | 延迟低不代表一定能建站 |
| **HTTPing** | 实际发 HTTP 请求，测到响应 | 更接近真实使用 | 慢，且受 CF 配额影响 |

**怎么选**：

- 只是挑 IP 填客户端 → TCPing 够用
- 想验证某个 IP 真的能打开你的站 → 开 HTTPing + 自定义测速域名
- 想按机房筛（如只要香港） → 必须 HTTPing（TCPing 拿不到 `colo`）

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| **线程数** | 200 | 并发测速数。越大越快，但占带宽和设备资源；弱设备建议 100~200 |
| **测速次数** | 4 | 每个 IP 测几次取平均。次数越多越稳定，耗时也越长 |
| **端口** | 443 | 列表项**没有自带端口**时使用的默认端口 |

> **注意**：如果 IP 列表里自带端口（如 `1.2.3.4:8443`），会**用自带的端口**测，不受这里影响。

### HTTPing 专属参数

| 参数 | 默认 | 说明 |
|---|---|---|
| **有效状态码** | 200 | 只填一个。默认还会接受 301 / 302 |
| **地区筛选** | 空 | IATA 机场码或国家码，如 `HKG,KHH,NRT,LAX`，英文逗号分隔 |

地区筛选的依据是 CF 响应里的 `colo` 字段，只有 HTTPing 模式能拿到。

## 自定义测速域名

> 位置：「延迟测速」卡片 → **自定义测速域名** 开关

### 它解决的问题

这是 **CFSTX 最重要的功能之一**。

默认用 `speed.cloudflare.com` 测速，验证的是「这个 IP 能否连上 Cloudflare」。但你在客户端里访问的是**自己的** Worker / Pages 域名。

**两者的路由并不完全重合。**

Cloudflare 的部分 Anycast IP 没有配置你域名的边缘路由，访问会返回：

- `403`（`error code: 1034`）
- 或直接超时

这就是「**CFSTX 里测速全部通过，填进客户端却大量 timeout**」的根因。

**实测数据**：某个 Worker 域名的 5955 个候选 IP 中，只有约 **1500 个（25%）** 真正服务它。

### 它怎么工作

开启后，在延迟测速之前插入一个探测阶段，对每个目标请求：

```text
https://<你的域名>/cdn-cgi/trace
```

- 返回 `200` 且响应体包含 `colo=` → 保留
- 其余 → 剔除

TLS 证书不做校验（CF 边缘对所有 IP 返回同一张证书，校验没意义）。

### 为什么不消耗 Workers 配额

`/cdn-cgi/trace` 由 Cloudflare **边缘节点直接生成响应**，请求根本不会进入 Worker 脚本，因此不计入 Workers 每日请求数。

可以放心对几千个地址做探测。

### 代价

每个候选 IP 多一次 HTTPS 请求（超时 5 秒，并发 300）。

6000 个目标大约增加 **1~2 分钟**。

### 什么时候用

| 场景 | 需要吗 |
|---|---|
| 部署了 Workers / Pages，通过自定义域名访问 | ✅ **强烈建议** |
| 准备把 IP 填进客户端订阅、Hosts 或 DDNS | ✅ **建议** |
| 只是访问 `cloudflare.com` 等 CF 官方站点 | ❌ 不需要，所有 IP 都服务它 |
| 域名没有接入 Cloudflare | ❌ 探测会全部失败 |

### 域名怎么写

**只填主机名本身**，不要带协议和路径：

| 写法 | 结果 |
|---|---|
| `fast3.example.com` | ✅ 正确 |
| `https://fast3.example.com/` | ✅ 可用（自动清理协议、路径、末尾斜杠、端口） |
| `fast3.example.com:8443` | ✅ 可用（端口被忽略，探测固定 443） |
| `  Fast3.Example.COM  ` | ✅ 可用（自动去空格、转小写） |
| `example.com`（只写根域） | ⚠️ 能探测通过，但根域不一定指向你的 Worker |
| `*.example.com` | ❌ 不接受，必须写具体子域 |

> [!TIP]
> **填你实际访问的那个子域名**，不要填根域。根域虽然也能探测通过，但不一定指向你的 Worker，选出来的 IP 可能对节点无效。

## 过滤条件

测完之后按这些条件筛，不符合的不进入结果。

| 条件 | 默认 | 说明 |
|---|---|---|
| **延迟上限** | 9999 ms | 只保留平均延迟低于该值的 |
| **延迟下限** | 0 ms | 排除延迟过低但速度差的节点 |
| **丢包率上限** | 1.00 | 范围 0~1，0 表示完全不允许丢包 |
| **速度下限** | 0 MB/s | 只保留下载速度高于该值，**需配合下载测速** |

> [!TIP]
> 中国大陆到 Cloudflare 的延迟经常在 **150~250ms**（走美西）。如果延迟上限设 150 一个都筛不出来，先改成 9999 看整体分布。

## 下载测速

对延迟最低的 N 个 IP 实际下载，测吞吐。

| 参数 | 默认 | 说明 |
|---|---|---|
| **测速数量** | 10 | 找到多少个满足条件的 IP 后停止 |
| **单 IP 时长** | 10 秒 | 每个 IP 的最大下载时间，太短会导致速度偏低 |
| **测速地址** | `speed.cloudflare.com/__down?bytes=90000000` | 需支持直连下载且文件较大 |
| **测速全部 IP** | 关 | 对 IP 段中每个 IP 测速（仅 IPv4），默认每段随机一个 |
| **禁用下载测速** | 关 | 只测延迟不测速度，结果按延迟排序 |

### 关于测速地址

默认用 Cloudflare 官方端点：

```text
https://speed.cloudflare.com/__down?bytes=90000000
```

> [!WARNING]
> 该端点**单次请求上限 100MB**，`bytes` 填超过 100000000 会返回 `403`。
> 程序默认用 90000000（90MB）规避。

如果默认地址失效或触发限流，可以换成自建的下载文件地址。

### 为什么很多 IP 速度显示 0.00

**这是正常的**：

- 默认只测延迟最低的 10 个，其余 IP 根本没做下载测速
- 下载测速是单线程排队执行，表格里未轮到的显示 0
- 进程还在跑的时候，后面的还没轮到

想测更多，把「测速数量」调大。

## 结果解读

### 评分公式

```text
评分 = 速度 50% + 延迟 35% + 丢包 15%
```

未开启下载测速（速度全为 0）时自动切换为：

```text
评分 = 延迟 70% + 丢包 30%
```

评分最高的 3 个标「推荐」并整行高亮。

### 表格各列

| 列 | 含义 |
|---|---|
| IP 地址 | 测速的 IP |
| 端口 | 实际使用的端口（来自列表或默认设置） |
| 平均延迟 | 多次测速的平均值 |
| 丢包率 | 失败次数占比 |
| 下载速度 | 实际下载吞吐，未测的显示 0 |
| 地区 | Cloudflare 机房代码（仅 HTTPing 有） |
| 评分 | 加权得分 |

### 导出

| 格式 | 内容 | 用途 |
|---|---|---|
| **CSV** | 完整字段 | Excel / 表格软件分析 |
| **TXT** | `IP:端口#地区 速度` | 直接作为 IP 列表再次测速 |

TXT 示例：

```text
27.44.142.135:10001#HKG 40.66MB/s
120.240.179.158:10001#HKG 25.22MB/s
104.234.174.220:443#SIN 12.06MB/s
```

### 复制

三种格式：

| 格式 | 示例 | 用在哪 |
|---|---|---|
| 纯 IP | `104.16.0.1` | 只需要 IP 的地方 |
| `IP:端口` | `104.16.0.1:443` | 客户端节点地址 |
| `IP:端口#地区` | `104.16.0.1:443#HKG` | 带备注的列表 |

## 场景预设

不知道参数怎么填时，直接点：

| 预设 | 适用场景 | 会做什么 |
|---|---|---|
| **新手推荐** | 第一次使用 | 内置 + 官方网段，只测延迟，2 分钟内出结果 |
| **Worker 专用** | 部署了 Workers / Pages | 开启域名探测，只保留真正服务你域名的 IP |
| **极速扫描** | 想快速看一眼 | 不测下载，延迟上限放宽到 300ms |

套用后所有字段仍可继续手动修改，不会锁死。

## 零结果诊断

一个 IP 都筛不出来时，会弹出诊断窗，按五步流程展示卡点，红色高亮失败的那一步：

| 步骤 | 为 0 说明 |
|---|---|
| ① 加载到的测速目标 | `ip.txt` 没找到 |
| ② 延迟测速连通 | 网络不通 / 开着 VPN |
| ③ 通过延迟、丢包过滤 | 延迟上限太严 |
| ④ 完成下载测速 | 测速地址被限流 |
| ⑤ 最高下载速度 | 下载全部失败 |

每一步都附带对应的调整建议。诊断窗内还能**导出运行日志**，方便反馈排查。

---

## 结果会保存吗

会。程序会把最近一次结果保存在内存中，**页面刷新不会丢**。

关闭程序后清空。
